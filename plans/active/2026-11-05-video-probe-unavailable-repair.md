## 方案 A：后端补丁与诊断交付（本次已确认的可执行范围）

### 1. 统一、受控的工具检查

新增后端共用的 ffprobe 运行检查模块，供解析、启动与部署诊断复用：

- 继续优先采用管理员配置的 FFPROBE_PATH，要求单个受信任可执行程序的绝对路径；未配置时保留现有 PATH 查找方式。
- 不写死 Mac 路径，不把 Windows 客户端系统当作服务器系统，不自动扫描磁盘或下载/执行未知二进制。
- 采用 execFile，不启用 shell。检查采用有限超时、有限输出与并发合并，区分路径不存在、权限不足、执行格式/架构错误、运行依赖异常、超时及异常输出。
- 工具运行检查不替代真实视频的容器、编码、轨道、像素和时长检查；已有完整解析仍保留。

拟新增 `services/domain/src/video-probe.mjs` 及必要的类型声明；解析器复用相同路径规则。位置可按既有模块依赖做等价小幅调整，不引入新技术栈或二进制安装依赖。

### 2. 提前检查，避免传完才报错

- API 启动时做一次受控检查，记录视频能力状态及脱敏诊断。
- 视频上传意图在身份、参数及相应资源权限检查后、接受文件字节之前，检查该依赖。不可用时返回明确的服务错误与 requestId，不创建无效上传记录或消耗完整文件传输。
- 对短期重复检查合并并使用短时缓存，故障恢复后可重新检查；不能无限缓存失败状态。`complete` 阶段仍执行真实解析，防止预检后工具状态变化被漏过。
- PDF、图片与已发布资料的读取保持可用，不因视频工具缺失将整个资料站停掉。
- `/health` 保留原有基础状态及字段，增加不含系统路径/堆栈的视频能力状态和检查时间。该接口只读取已知检查状态，不让公开请求无限触发子进程；未检查必须明确标识，不能默认为可用。
- 继续使用前端已能识别的 VIDEO_PROBE_UNAVAILABLE 等错误分类；不靠修改文案伪装修复。

拟涉及 `services/api/src/main.ts`、`services/mock-api/src/main.ts`、`services/domain/src/http.ts`、必要的 backend 上传入口、`services/mock-api/src/parse-file.mjs`。不修改二维码模块。

### 3. 交付给部署工程师的一条自检命令

增加 `scripts/check-video-runtime.mjs` 和 `package.json` 中的 `check:video-runtime` 命令。工程师在实际 API 运行账号和环境中执行：

`pnpm check:video-runtime`

输出服务器系统/架构、工具路径来源、可执行状态、明确原因和针对性下一步；失败返回非零退出码，可作为部署门槛。脚本不连接数据库、不修改配置、不重启服务、不下载软件，不输出完整环境变量、令牌或密码。路径等运维信息只在工程师命令行报告中出现，不回传前台。

文档提供 Linux、Windows Server、容器的检查与环境注入说明；容器强调在运行镜像内具备工具，Windows 使用服务器自身的 ffprobe.exe 路径。对于云函数等受限运行时，说明须核实执行能力和依赖打包，不能承诺一条安装命令适配所有平台。

拟涉及 `.env.example`、`README.md`、`deployment.md`、`docs/large-upload-and-video.md`，以及一份集中运维说明。此次不更改线上配置、不新建猜测的生产部署文件。
